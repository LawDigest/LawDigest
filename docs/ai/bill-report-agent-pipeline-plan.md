# 법안 리포트 에이전트 파이프라인 계획

작성일: 2026-06-10

## 1. 목적

법안 ID 하나로 시민이 읽을 수 있는 법안 리포트를 만든다.

이번 계획의 핵심은 두 단계 분리다.

```text
bill_id 입력
→ 1차 에이전트: 관련 정보 수집 + 텍스트 리포트 생성
→ 2차 에이전트: 텍스트 리포트 분석 + visualize_guide.md 기반 컴포넌트 선택
→ 선택한 컴포넌트에 필요한 JSON 데이터 생성
→ 프론트: JSON과 최신 동적 데이터를 조합해 렌더링
```

AI는 법안의 내용과 맥락을 설명한다. 현재 심사 단계, 처리 결과, 투표 결과, 조회수, 스크랩 수처럼 계속 바뀌는 값은 AI 리포트에 고정하지 않는다.

## 2. 주요 원칙

### 2.1 관련 정보라는 용어를 사용한다

리포트 생성에 쓰는 자료는 "근거"가 아니라 "관련 정보"로 부른다.

관련 정보는 법안 이해를 돕는 입력이다. 에이전트는 관련 정보를 수집하고, 관계없는 정보와 위험한 정보를 걸러낸 뒤 리포트를 작성한다.

### 2.2 AI 생성물과 동적 데이터를 분리한다

AI 생성물에 포함한다.

- 법안의 핵심 내용
- 쉬운 요약
- 주요 내용
- 현행 제도와 달라지는 점
- 관련 법률과 조문
- 영향을 받는 대상
- 함께 볼 정보
- 확인이 필요한 정보

프론트와 DB/API가 별도로 다룬다.

- 현재 심사 단계
- 단계별 진행 상태
- 처리 결과
- 투표 결과
- 조회수
- 스크랩 수
- 사용자 액션 상태

심사 단계는 변동성이 크다. 프론트는 항상 최신 API 데이터를 받아 별도 UI로 표시한다.

### 2.3 쉬운 요약은 토스식 설명조를 따른다

쉬운 요약은 해요체로 쓴다. 문장은 짧게 쓴다. 법률 용어는 시민이 이해할 수 있는 말로 풀어쓴다.

참고 기준:

- 토스 UX Writing Guide: https://developers-apps-in-toss.toss.im/design/ux-writing.html
- 토스의 8가지 라이팅 원칙들: https://toss.tech/article/8-writing-principles-of-toss

작성 규칙:

- 해요체를 사용한다.
- 능동형 문장을 우선한다.
- 부정형보다 긍정형을 우선한다.
- 한 문장에 한 가지 내용만 담는다.
- 어려운 법률 용어를 그대로 두지 않는다.
- 정치적 평가를 섞지 않는다.
- 사용자를 불안하게 만드는 표현을 피한다.

예시:

```text
나쁨:
본 법안은 상임위원회의 활동 결과보고서 제출 의무를 명문화하여 입법부의 책임성과 투명성을 제고하려는 취지입니다.

좋음:
국회 상임위원회가 한 일을 보고서로 남기게 하는 법안이에요. 국정감사에서 다룬 주요 내용도 같이 적도록 해서, 시민이 나중에 확인할 수 있는 기록을 늘리려는 내용이에요.
```

### 2.4 검색 도구를 허용하되 필터링을 강제한다

1차 에이전트는 관련 뉴스와 설명 자료를 검색할 수 있다. 검색 결과는 바로 리포트에 쓰지 않는다.

필터 기준:

- 법안명, 개정 대상 법률, 핵심 쟁점 중 하나와 직접 연결된 자료만 사용한다.
- 단순히 같은 의원, 같은 정당, 같은 시기에 나온 기사라는 이유만으로 포함하지 않는다.
- 공공기관, 국회, 법제처, 국가법령정보센터, 주요 언론, 전문기관 자료를 우선한다.
- 블로그, 커뮤니티, SNS 단독 주장은 사용하지 않는다.
- 사설, 칼럼, 논평은 사실관계와 의견을 분리한다.
- 특정 정당이나 정치인에 대한 평가 표현은 리포트에 넣지 않는다.
- 출처와 날짜를 확인할 수 없는 수치, 인용, 사건은 단정하지 않는다.
- 교차 확인이 어려운 정보는 `확인 필요`로 보낸다.

## 3. 1차 에이전트: 관련 정보 수집형 텍스트 리포트

### 3.1 입력

```json
{
  "bill_id": "PRC_X2Y6W0W4U1R4R1P1Q0O8P2N7O7V1U5"
}
```

### 3.2 사용 가능한 정보 출처

- 열린국회정보 MCP
- 국가법령정보센터 MCP
- 법제처 MCP
- 내부 DB/API
- 검색 도구

### 3.3 수집할 관련 정보

의안 기본 정보:

- 법안명
- 의안번호
- 발의자
- 소관위원회
- 개정 대상 법률

의안 내용 정보:

- 제안이유
- 주요내용
- 개정 대상 조문
- 신설, 삭제, 수정되는 표현
- 의안 원문 또는 PDF 링크

현행 법령 정보:

- 현재 시행 중인 조문
- 해당 조문의 위치
- 연결 조문
- 관련 시행령과 시행규칙

맥락 정보:

- 같은 법률을 고치는 다른 법안
- 같은 주제를 다루는 법안
- 유사 법안의 처리 결과
- 관련 뉴스와 설명 자료

이해관계 정보:

- 영향을 받을 기관
- 영향을 받을 시민
- 영향을 받을 단체나 사업자
- 행정 절차 변화
- 보고 의무, 비용, 조직 변화 가능성

### 3.4 1차 산출물

1차 에이전트는 Markdown 텍스트 리포트를 만든다.

```markdown
# 법안 텍스트 리포트

## 한 줄 요약
...

## 쉬운 요약
...

## 주요 내용
...

## 현행 제도와 달라지는 점
...

## 관련 법률·조문
...

## 영향을 받는 대상
...

## 함께 볼 정보
...

## 확인이 필요한 정보
...
```

### 3.5 1차 에이전트 금지 사항

- 현재 심사 단계를 본문에 쓰지 않는다.
- 처리 결과와 투표 결과를 본문에 쓰지 않는다.
- 조회수, 스크랩 수, 사용자 반응 데이터를 쓰지 않는다.
- 확인하지 못한 내용을 추측하지 않는다.
- 찬반 의견을 만들지 않는다.
- 법률 자문처럼 쓰지 않는다.
- 특정 정치 세력에 유리하거나 불리한 표현을 만들지 않는다.

## 4. 2차 에이전트: 텍스트 리포트의 시각화 JSON 변환

### 4.1 입력

```json
{
  "bill_id": "PRC_X2Y6W0W4U1R4R1P1Q0O8P2N7O7V1U5",
  "text_report": "1차 에이전트가 생성한 Markdown 리포트",
  "visualize_guide_path": "docs/ai/visualize_guide.md"
}
```

### 4.2 처리 순서

1. `docs/ai/visualize_guide.md`를 읽는다.
2. 사용 가능한 컴포넌트 목록, 사용 조건, 필수 JSON 필드를 확인한다.
3. 텍스트 리포트에 어떤 정보가 있는지 분석한다.
4. 사용할 컴포넌트를 동적으로 선택한다.
5. 선택한 컴포넌트의 선택 이유를 기록한다.
6. 선택한 컴포넌트에 필요한 JSON 데이터만 생성한다.

2차 에이전트는 모든 법안에 같은 컴포넌트 구조를 강제하지 않는다. 법안 내용에 맞는 컴포넌트만 고른다.

### 4.3 2차 산출물

```json
{
  "bill_id": "PRC_X2Y6W0W4U1R4R1P1Q0O8P2N7O7V1U5",
  "selected_components": [
    {
      "component": "summary_callout",
      "reason": "한 줄 요약과 쉬운 요약에서 핵심 메시지가 분명함"
    },
    {
      "component": "before_after",
      "reason": "현행 제도와 개정안의 차이가 리포트에 명시되어 있음"
    }
  ],
  "blocks": [
    {
      "type": "summary_callout",
      "data": {
        "title": "상임위 활동을 보고서로 남기게 하는 법안이에요.",
        "body": "국정감사에서 다룬 주요 내용도 보고서에 포함해 시민이 확인할 수 있는 기록을 늘리려는 내용이에요."
      }
    },
    {
      "type": "before_after",
      "data": {
        "current": "상임위원회 활동 결과보고서 제출 의무가 명확하지 않아요.",
        "proposed": "임기 종료 시점에 활동 결과보고서를 제출하도록 해요.",
        "change_summary": "국회 상임위원회 활동을 공식 기록으로 남기는 절차가 더 분명해져요."
      }
    }
  ]
}
```

### 4.4 2차 에이전트 금지 사항

- 텍스트 리포트에 없는 사실을 추가하지 않는다.
- 새로운 법률 해석을 만들지 않는다.
- 현재 심사 단계 UI를 만들지 않는다.
- 처리 결과와 투표 결과를 AI JSON에 고정하지 않는다.
- `visualize_guide.md`에 없는 컴포넌트를 만들지 않는다.
- 컴포넌트 스타일, 색상, Tailwind class를 생성하지 않는다.

## 5. visualize_guide.md 역할

`docs/ai/visualize_guide.md`는 2차 에이전트가 읽는 컴포넌트 선택 가이드다.

문서에 포함할 내용:

- 컴포넌트 이름
- 컴포넌트 목적
- 사용 조건
- 사용하지 말아야 하는 경우
- 필수 JSON 필드
- 선택 예시
- 프론트 렌더링 주의사항

초기 컴포넌트 후보:

- `summary_callout`: 핵심 메시지 강조
- `before_after`: 현행 제도와 개정안 비교
- `change_points`: 달라지는 점 목록
- `affected_parties`: 영향을 받는 대상 목록
- `related_laws`: 관련 법률과 조문
- `term_glossary`: 어려운 용어 풀이
- `comparison_table`: 여러 대상이나 제도 비교
- `related_info_list`: 관련 뉴스, 설명 자료, 유사 법안
- `check_needed`: 확인이 필요한 정보

현재 심사 단계, 단계별 날짜, 처리 결과, 투표 결과는 이 문서의 AI 생성 컴포넌트에 포함하지 않는다. 해당 정보는 프론트가 기존 데이터로 렌더링한다.

## 6. 구현 계획

### Sprint 1: 텍스트 리포트 생성 검증

목표: `bill_id` 하나로 1차 에이전트가 관련 정보를 수집하고 텍스트 리포트를 생성한다.

검증:

- 샘플 법안 1건으로 텍스트 리포트를 생성한다.
- 사용자가 리포트 품질을 직접 검토한다.
- 기존 `gpt_summary`보다 정보가 풍부한지 확인한다.

작업:

1. 1차 에이전트 시스템 프롬프트 작성
2. 관련 정보 수집 체크리스트 작성
3. 검색 결과 필터링 규칙을 프롬프트에 반영
4. 샘플 `bill_id`로 실행
5. 결과를 사람이 검토

완료 기준:

- 쉬운 요약이 해요체 설명문으로 나온다.
- 현행 제도와 달라지는 점이 분리되어 나온다.
- 관련 법률과 조문이 별도 섹션으로 나온다.
- 관련 뉴스와 정보는 필터링 후 필요한 것만 남는다.
- 확인하지 못한 내용은 `확인 필요`로 표시된다.

### Sprint 2: visualize_guide.md 작성

목표: 2차 에이전트가 컴포넌트를 동적으로 선택할 수 있는 가이드를 만든다.

검증:

- 각 컴포넌트에 목적, 사용 조건, 필수 필드가 있다.
- 현재 심사 단계 같은 동적 데이터가 제외되어 있다.
- 2차 에이전트가 이 문서만 보고 선택과 JSON 생성을 할 수 있다.

작업:

1. `docs/ai/visualize_guide.md` 생성
2. 초기 컴포넌트 목록 정의
3. 컴포넌트별 JSON 필드 정의
4. 사용 조건과 제외 조건 작성
5. 예시 JSON 작성

완료 기준:

- 문서에 없는 컴포넌트를 에이전트가 만들 수 없게 규칙이 명확하다.
- 모든 컴포넌트가 프론트 렌더링 가능한 데이터 필드를 가진다.
- 필수 컴포넌트와 선택 컴포넌트가 구분된다.

### Sprint 3: 시각화 JSON 변환 검증

목표: 1차 텍스트 리포트를 입력으로 받아 2차 에이전트가 컴포넌트를 선택하고 JSON을 만든다.

검증:

- 2차 에이전트가 `visualize_guide.md`를 먼저 읽는다.
- 선택한 컴포넌트와 선택 이유를 반환한다.
- 선택한 컴포넌트에 대한 JSON 데이터만 생성한다.

작업:

1. 2차 에이전트 시스템 프롬프트 작성
2. 1차 텍스트 리포트를 입력으로 전달
3. 선택 컴포넌트 목록 확인
4. JSON 구조 확인
5. 프론트 렌더링 후보와 비교

완료 기준:

- 모든 `blocks[].type`이 `visualize_guide.md`에 정의되어 있다.
- JSON에 텍스트 리포트에 없는 사실이 없다.
- 같은 법안이라도 텍스트 리포트 내용에 따라 컴포넌트 선택이 달라질 수 있다.

### Sprint 4: 제품 연결 설계

목표: 검증이 끝난 리포트 생성 구조를 서비스 파이프라인에 연결할 위치를 정한다.

검증:

- 기존 `brief_summary`, `gpt_summary`, `summary_tags` 흐름을 깨지 않는다.
- 새 리포트 저장 위치와 재생성 정책이 정해진다.
- 동적 데이터는 기존 API 또는 별도 API로 유지된다.

작업:

1. AI 서비스에 1차 텍스트 리포트 생성 함수 추가 위치 결정
2. 2차 시각화 JSON 변환 함수 추가 위치 결정
3. DB 저장 컬럼 또는 별도 테이블 설계
4. 백엔드 응답 DTO 설계
5. 프론트 렌더러 컴포넌트 설계

완료 기준:

- 기존 상세 페이지 요약이 깨지지 않는다.
- 리포트 생성 실패가 기존 법안 노출을 막지 않는다.
- 심사 단계와 투표 결과는 최신 데이터 UI로만 표시된다.

## 7. 검증 기준

텍스트 리포트 품질:

- 기존 요약보다 구체적인가
- 법률 용어를 시민 언어로 풀었는가
- 현행 제도와 개정안 차이를 설명했는가
- 영향을 받는 대상을 구체적으로 나눴는가
- 검색 결과에서 관련 없는 뉴스와 편향적 정보를 제거했는가
- 확인하지 못한 내용을 추측하지 않았는가

시각화 JSON 품질:

- 컴포넌트 선택 이유가 납득되는가
- 선택한 컴포넌트가 리포트 내용과 맞는가
- JSON 필드가 프론트 렌더링에 충분한가
- 동적 데이터가 AI JSON에 들어가지 않았는가
- 텍스트 리포트에 없는 사실이 추가되지 않았는가

## 8. 리스크와 대응

검색 결과가 법안과 약하게 연결될 수 있다.

- 대응: 법안명, 개정 대상 법률, 핵심 쟁점 중 하나와 직접 연결되지 않으면 제외한다.

뉴스가 정치적 논평을 포함할 수 있다.

- 대응: 사실관계만 추출하고 평가는 버린다. 의견이 분리되지 않으면 사용하지 않는다.

2차 에이전트가 새 사실을 만들 수 있다.

- 대응: 2차 에이전트는 텍스트 리포트 변환만 허용한다. 추가 해석을 금지한다.

시각화 JSON 구조가 매번 달라 프론트 구현이 어려울 수 있다.

- 대응: 컴포넌트 종류와 컴포넌트별 필드는 `visualize_guide.md`에서 고정한다. 달라지는 것은 선택된 컴포넌트 목록과 순서다.

심사 단계가 리포트 텍스트에 들어갈 수 있다.

- 대응: 1차와 2차 프롬프트 모두에 동적 데이터 제외 규칙을 넣는다. 검증 기준에도 포함한다.
