# 법안 리포트 프롬프트·검증 계약

작성일: 2026-06-23

이 문서는 `build_bill_report_prompt`와 `_validate_report_body`가 강제하는 출력 계약을 정리한다. 운영자는 이 문서를 보고 생성 결과가 왜 실패했는지, 프롬프트를 바꿀 때 어떤 표면 형식을 유지해야 하는지 확인할 수 있다.

## 1. 리포트 기본 구조

최종 출력은 `brief_summary`, `report_body`, `tooltips`, `rejected`를 담은 구조화 JSON만 허용한다. 내부 조사 과정, MCP 호출 목록, 실패 로그, 리서치 메모는 본문에 쓰지 않는다.

필수 섹션:

```markdown
# 법안명

## 쉬운 요약
- ...

## 주요 내용
- **항목 제목**: 쉬운 설명

## 왜 나왔나
...

## 무엇이 달라지나

### 1) 짧은 명사형 제목

원문 조문 변화 요약 문단.

- 용어명: 필요한 경우에만 설명
- 사용자에게 필요한 쉬운 풀이

## 누구에게 영향이 있나
...

## 봐야 할 점
...

## 확인한 근거
- 기관명: 확인한 문서·항목
```

검증상 필수 섹션은 `## 쉬운 요약`, `## 주요 내용`이다. 다른 섹션은 프롬프트 계약상 요구된다.

## 2. 카드용 제목

`brief_summary`는 카드의 `h2`에 표시할 제목형 요약이다.

- 원문 `summary`나 `쉬운 요약`의 첫 문장을 그대로 복사하지 않는다.
- `[핵심 변경 목적/수단]을/를 위한 [정확한 법안명]` 구조로 작성한다.
- 여러 변화가 있으면 가장 중요한 2~3개를 짧은 명사형으로 묶는다.
- 완결된 설명문이나 `입니다`, `합니다`, `함` 같은 종결 표현을 쓰지 않는다.
- 핵심 변경 부분은 80자를 넘기지 않는다.

예시:

```text
선관위원장 상임화·상임위원 확대 및 감사·인사검증 강화를 위한 선거관리위원회법 일부개정법률안
```

## 3. 쉬운 요약

`쉬운 요약`은 법안이 하려는 일을 먼저 말한다.

권장 형식:

```markdown
- ...하기 위한 법률 개정안이에요.
```

규칙:

- 5개 불릿을 기본으로 한다.
- 복합 개정안은 정보를 줄이지 않는다.
- 처리 상태를 첫 문장으로 앞세우지 않는다.
- `아직 법으로 확정된 건 아니고`처럼 상태 안내를 습관적으로 붙이지 않는다.
- 현재 심사 단계, 공포일, 본회의 표결수 같은 동적 상태값은 프론트 데이터가 따로 보여준다.

## 4. 주요 내용

각 항목은 반드시 `**항목 제목**: 쉬운 설명` 형식이다.

좋은 예:

```markdown
- **부당한 표시·광고 제한**: 허위·과장 등 소비자를 오도할 수 있는 표현을 규제해요.
```

나쁜 예:

```markdown
- 권한 정비: 필요한 설명이에요.
- 핵심: 권한 정비
  설명: 필요한 설명입니다.
```

규칙:

- 콜론 앞 핵심 라벨은 Markdown 볼드체여야 한다.
- `핵심:`, `설명:` 같은 메타 라벨을 출력하지 않는다.
- 법안에 여러 제도 변화가 있으면 5~7개 항목까지 늘린다.
- 짧게 쓴다는 이유로 근거, 영향, 예외를 덜어내지 않는다.

## 5. 무엇이 달라지나

이 섹션은 피드보다 상세 화면에서 더 중요하다. 각 변화 묶음은 번호 헤딩, 원문 요약 문단, 설명/풀이 불릿 순서를 따른다.

형식:

```markdown
### 1) 온라인 유통질서 규율 조항군 신설

기존 조문 체계에서 제23조는 주로 허가 취소 절차의 청문 규정이었으나, 제안안은 이를 온라인 유통질서 규율 조항군으로 넓혀요. 허위정보 유포, 인터넷 표시·광고, 플랫폼 운영자의 행위까지 함께 다루도록 조문 위치와 범위를 바꿔요.

- 청문 규정: 여기서 `청문`은 처분을 받기 전에 당사자가 설명하고 반론할 수 있는 절차에요.
- 사용자 입장에서는, 문제가 터진 뒤에 벌을 주는 데서 그치지 않고 거래 전에 정보가 맞는지 더 일찍 걸러내겠다는 뜻이에요.
```

제목 규칙:

- `### 1) 제목` 형식으로 쓴다.
- 제목은 설명문이 아니라 짧은 명사형으로 쓴다.
- `허위개발정보 유포를 금지하는 조문을 새로 둔다`보다 `허위개발정보 유포를 금지하는 조문 신설`을 쓴다.
- `벌칙·과태료 체계 개정과 집행주체 확충`처럼 행정문서식 표현은 피한다.
- `허위정보·부당광고 위반 시 제재 강화`처럼 사용자가 바로 이해할 수 있는 제목을 쓴다.

본문 규칙:

- 번호 헤딩 바로 아래에는 불릿이 아니라 일반 문단을 둔다.
- 원문 요약 문단은 2문장 기준이다.
- 그 아래 설명/풀이를 2~3개 불릿으로 붙인다.
- 불릿만으로 변화 묶음을 시작하지 않는다.

## 6. 법률·행정용어 풀이

어려운 용어는 괄호 안에 끼워 넣지 않고 별도 불릿으로 설명한다.

설명해야 하는 대표 용어:

- `청문`, `청문 규정`, `청문 절차`
- `과태료`
- `위임·위탁`

형식:

```markdown
- 청문 규정: 여기서 `청문`은 처분을 받기 전에 당사자가 설명하고 반론할 수 있는 절차에요.
- 과태료: 행정질서 위반에 부과하는 금전 제재에요.
- 위임·위탁: 행정기관의 권한이나 업무 일부를 다른 기관이 맡아 처리하게 하는 방식이에요.
```

설명하지 않을 용어:

- `허위정보`
- `허위정보 유포`
- `필수정보`
- `표시·광고`

이 말들은 뜻이 비교적 바로 드러난다. 사전식 설명을 붙이기보다 사용자에게 어떤 변화가 생기는지 바로 풀어쓴다.

## 7. 금지 표현

아래 표현이 본문에 남으면 검증 실패다.

- `Lawdigest 요약 개선 제안`
- `사용한 MCP 도구`
- `MCP 도구`
- `원문 요약:`
- `용어 설명:`
- `법령 체계:`
- `쉬운 풀이:`
- `mcp__`
- `` `get_ ``, `` `search_ ``, `` `legal_ ``, `` `query_ ``
- `내부 조사`
- `리서치 메모`

쉬운 풀이 문장도 고정 접두어를 반복하지 않는다.

반복 금지:

- `쉽게 말하면,`
- `쉽게 말해,`
- `한마디로,`

한 번은 쓸 수 있지만 여러 변화 묶음에서 반복하면 기계적으로 보인다.

## 8. 문체

문체는 자연스러운 `-요` 체를 쓴다.

피해야 할 종결:

- `합니다.`
- `됩니다.`
- `입니다.`
- `바뀝니다.`

좋은 방향:

- `바뀌어요.`
- `볼 수 있어요.`
- `줄어들어요.`

어색한 변환도 금지한다.

- 나쁨: `줄어드어요.`
- 좋음: `줄어들어요.`

## 9. 강조 표시

리포트에는 시각적 강조가 있어야 한다.

- 중요한 단어: `**중요 단어**`
- 중요한 문장: `<mark>중요 문장</mark>`

강조는 과하게 쓰지 않는다. 프론트는 `<mark>`를 정당색 기반 하이라이트로 렌더링한다.

## 10. DB 반영용 변환

DB 반영 시 `_build_db_summary_payload`가 Markdown을 가공한다.

- 최상단 `# 법안명`은 제거한다.
- `## 확인한 근거` 이후는 `gpt_summary`에서 제거한다.
- 구조화 출력의 `brief_summary`가 제목형 계약과 정확한 법안명 suffix를 만족하는지 검증한다.
- 검증된 `brief_summary`로 기존 값을 교체한다.
- 구조화 출력 이전의 레거시 Markdown만 기존 값 유지·첫 불릿 fallback 변환을 사용한다.
- `summary_tags`는 기존 값을 유지한다.

## 11. 테스트 기준

프롬프트·검증 계약은 `services/ai/tests/processor/test_agentic_bill_report.py`가 고정한다.

중요 테스트 축:

- MCP 조사 원칙이 프롬프트에 들어가는지
- 사용자-facing 리포트 형식인지
- 내부 도구명과 메타 라벨을 거부하는지
- 어려운 용어 설명과 불필요한 용어 설명을 구분하는지
- 번호 헤딩과 명사형 제목을 요구하는지
- 볼드체, 하이라이트, 해요체를 요구하는지
- Codex 실행 명령에 4개 MCP 서버가 들어가는지
- manifest에 시간·토큰·사용량 계측이 남는지
- 병렬 세션 실행이 동작하는지
