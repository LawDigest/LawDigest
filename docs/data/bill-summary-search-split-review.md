# Bill summary storage and search split review

Date: 2026-06-27

## Current state

- `Bill.summary` stores the original bill summary text.
- `Bill.summary` is also part of user search through `MATCH(summary) AGAINST (...)`.
- The production `Bill` table has a `FULLTEXT KEY summary (summary)`.
- `gpt_summary` and `brief_summary` also have FULLTEXT indexes, and production currently has duplicated FULLTEXT indexes for both columns:
  - `gpt_summary`, `gpt_summary_2`
  - `brief_summary`, `brief_summary_2`
- `Bill.summary` has no remaining `NULL` or empty-string rows in production, but the column is still nullable at the schema level.

## Diagnosis

The problem is not just that `summary` was nullable. The larger coupling is that one column is doing two jobs:

1. It is the canonical source text used to decide whether a bill is eligible for ingestion.
2. It is also a search-indexed document field.

That coupling makes a data-quality constraint on the canonical source text require a costly search-indexed table rebuild. A direct `ALTER TABLE Bill MODIFY COLUMN summary TEXT NOT NULL` used MySQL's table-copy path in production and held metadata locks long enough to block concurrent `Bill` updates.

## Options

### Option A: Keep search on `Bill.summary`

Keep the current shape and apply `summary TEXT NOT NULL` with `pt-online-schema-change`.

Pros:
- Smallest application change.
- Keeps existing search query shape.

Cons:
- `Bill` remains a large write-heavy table with FULLTEXT search indexes.
- Future source-text changes still rebuild the main table and its search indexes.
- Search index cleanup and source-data constraints remain coupled.

### Option B: Add another search column on `Bill`

Keep `Bill.summary` as canonical source text and add a separate `Bill.search_text` or `Bill.summary_search_text` column with FULLTEXT indexing.

Pros:
- Separates semantic meaning inside code.
- Search query can target a precomposed field.

Cons:
- Still puts FULLTEXT indexing on the main `Bill` table.
- Still makes `Bill` DDL expensive.
- Adds another large text column to the same hot table.

### Option C: Move search text into a separate table

Create a separate table, for example:

```sql
CREATE TABLE BillSearchDocument (
    bill_id VARCHAR(255) NOT NULL,
    search_text MEDIUMTEXT NOT NULL,
    modified_date DATETIME(6) NULL,
    PRIMARY KEY (bill_id),
    FULLTEXT KEY ft_bill_search_text (search_text),
    CONSTRAINT fk_bill_search_document_bill
        FOREIGN KEY (bill_id) REFERENCES Bill (bill_id)
        ON DELETE CASCADE
);
```

`search_text` can be generated by combining `bill_name`, `brief_summary`, `gpt_summary`, and optionally `summary`.

Pros:
- Keeps `Bill.summary` as canonical source data.
- Moves FULLTEXT rebuild cost out of the main `Bill` table.
- Search documents can be rebuilt independently from ingestion.
- A failed search-document rebuild does not corrupt canonical bill rows.

Cons:
- Requires backend search query changes.
- Requires a backfill and ongoing sync path.
- Search relevance needs retuning because the current query ranks fields separately.

## Recommendation

Do not split by adding another FULLTEXT column to `Bill`. That does not solve the structural problem.

Use this sequence instead:

1. Keep `Bill.summary` as the canonical original summary and enforce it as required.
2. Apply `summary TEXT NOT NULL` with `pt-online-schema-change`.
3. Remove duplicated FULLTEXT indexes on `gpt_summary` and `brief_summary` after confirming query plans.
4. Introduce `BillSearchDocument` as a separate search table.
5. Move backend search from direct `MATCH(...)` on `Bill` columns to `BillSearchDocument`.
6. After search has moved, drop FULLTEXT indexes from `Bill.summary`, `Bill.gpt_summary`, and `Bill.brief_summary` if no other query uses them.

This keeps the immediate data-quality fix small while giving us a path to uncouple source-data constraints from search-index maintenance.

## Initial implementation

The first implementation introduces `BillSearchDocument` as an asynchronously rebuilt table.

- Schema migration: `infra/db/migrations/20260627_create_bill_search_document.sql`
- Rebuild runtime command:
  ```bash
  uv run python -m lawdigest_data.runtime.cli bill-search-rebuild --mode prod --limit 500
  ```
- Airflow DAG: `bill_search_rebuild_dag`
- Backend search source: `BillSearchDocument.search_text`

The rebuild job selects `READY` bills whose search document is missing or stale, rebuilds weighted search text from bill fields, and upserts `BillSearchDocument` independently from the bill ingestion path.
